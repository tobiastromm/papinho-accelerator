## Exact normative boundaries

C2 revision1 section4, policy_epoch paragraph (docs/protocol/pacc-c2-specification-revision-1.0.md:223): epoch is assigned from server current policy; every operation-bound use compares immutable epoch plus live policy locally. Section4 BIND rule at237 requires exact Session/Principal, current policy, expiry and token validation. Section6 at265 forbids new payload after local revocation; accepted lower-layer bytes may still escape and narrow CANCEL/FINAL authority does not restore DATA permission. ADR0012 Decision requires immutable upper-bound Session snapshot PLUS current contextual enforcement; disable/revocation can deny immediately, no silent capability expansion. ADR0048 Lifecycle requires mandatory participants, confirmed commit and publication before normative CURRENT, epoch only after valid normative commit, retained leases and callbacks. Accepted CA technical profile2.2/2.5 requires same-root actual CURRENT CAS and distinct reservation/publication transactions;2.4/3.5/3.6 require anti-rollback checkpoint/fencing before authoritative recovery. Model E ADR0033 distinguishes close attempt from factual DESTROYED and terminal unresolved retention. The accepted coexistence decision expressly supplements, not replaces, those contracts.

No conflict between those accepted decisions is established: retaining old bytes/identity does not grant continued unlimited authority. The invalid interpretation is treating an old held revision as sufficient CURRENT for new effects. Such an interpretation would require an explicit normative exception and is not proposed or accepted here.

C2 operations currently share one generic Session gate: c2_session.c papacc_c2_session_authorized calls launcher_c2_session_current; c2_operation_win32.c session_ok is used by both open and live. open at62 sets op.epoch=session.policy_epoch. live at28 checks that immutable equality and then invokes current policy at33. Replacing the generic Session gate with held-pin validity changes BOTH A and B. The rejected hunk cannot establish the necessary distinction. Existing BIND, deadline, token/Principal and flow gates must remain untouched.

## Proof limitations and concrete blocked items

The binding design establishes data lifetime only. H09 deliberately retains existing strict listener-current comparisons. It therefore cannot be advertised as maintaining old Session operation authority after a genuine C2 policy epoch change. New Session authorization likewise remains dependent on actual published application CURRENT and existing C2 association. The full live transaction is not supplied by the foundation patch.

To finish the live proposal, resolve the mapping between administrative issuer-only revision/context epoch and C2 policy_epoch. Two counterexamples must be excluded: (1) increment current_policy_epoch on every issuer metadata commit invalidates old Session/operation comparisons despite unchanged operational policy; (2) ignoring current_policy_epoch for any held Session also enables new OPEN under stale authority. The accepted coexistence record does not explicitly define that mapping or a new per-operation admission API. No arbitrary new rule is accepted by this review.

If issuer-only metadata changes are specified not to advance the C2 operational policy epoch while policy/grants/security inputs are unchanged, record that precise mapping with same-root administrative revision/context publication and new Session CURRENT binding; no second epoch authority or wire change. If C2 policy really changes, retain immutable captured operation epoch and re-evaluate live policy under the existing section4/ADR0012 obligations, while denying new admissions under obsolete policy. This requires a distinct new-effect path and continuation proof, not removal of the generic guard. If either choice modifies an accepted obligation, explicit normative acceptance must precede code. No exception permitting stale epoch for new admission is proposed.

Publication still needs: factual mandatory participants/actor/ED11 identity, native durable CAS, authoritative current-snapshot reference, atomic root publication/epoch acknowledgement, retained generations, stale writer/crash/Stop handling, and a reviewed nonblocking administrative transaction boundary. Existing TxF writes/RNG run synchronously; a pure copy proof does not prove bounded latency for active persistence/provider calls. No new worker/supervisor is authorized by this proposal.

Recovery remains DENY: a hash-valid image or exclusive read handle is not latest high-water/fencing. No checkpoint producer was identified or invented. Normative CNG key correspondence, backup/restore gates and generation-prefix history proofs are not fabricated.

## Reaper release proof obligations

The existing reaper requires REVOKED initialized exact Session, absence of native Session and control Connection, no operation pointer even in EMPTY slots, no writer/denial references, no initialized channel reference, no active processor reference, and all matching secure candidates CLOSED with no PST connection/retained-terminal processor/published security/registered adapter/native Connection. Existing owner_reap_completed must have resolved operations first. H17 independently repeats these conditions; H18 calls it before clearing manager links and Session metadata. No shortening to Session.state or native-ID lookup is allowed.

Stop/error-terminal can prevent reaping; pins then remain charged and prevent root finish. Failed unpin never zeroes the root container or Session. A retained field is not cleared by timeout/retry. This is a static ordering argument; native fault/quiescence tests remain required. The proposed patch must be applied as one reviewed unit with declarations/helper/caller dependencies; H09 alone would deny Sessions without acquired pins. It is not suitable for migrating already-initialized Sessions lacking factual pins; never reconstruct their admission retrospectively.
