## Existing owner and integration

PS_NATIVE in server_service_win32.c remains the single native SCM administrative owner. Its private admission member and server_service_admission_win32.inc implement the native primitive. No launcher-local coordinator owns the decision. PS_LAB_BINDING remains a DATA receipt, never an authority producer. The durable launcher root calls the same service-owner API; fields are not copied into another manager.

Explicit PAPACC_ENABLE_SINGLE_LAB_ADMISSION opt-in selects only this fixed qualification profile. It is OFF by default. Compilation of the selected profile propagates the specialization to the same service library/root/qualifier. Production/default/0.6.4 behavior and the pinned service candidate are unchanged. Private Windows APIs/types do not enter portable DATA/wire. New fixed operation paths are inside the LAB-only specialization, not general product deployment paths. The API has no alternate attempt, environment fallback, arbitrary service selector or credential producer.

## Native mechanism and invariants

The same owner uses Global\PapinhoAccelerator.ED11.SingleLabAdmission, explicitly across Windows sessions. Security descriptor grants only the fixed operator, SYSTEM and Administrators; the returned owner/three ACEs/flags/principals/masks are validated. GENERIC_ALL and its exact MUTEX_ALL_ACCESS mapping are equivalent for this object, not arbitrary ignored rights. A pre-created object with another descriptor denies. Wait is zero-time; BUSY does not grant admission. WAIT_ABANDONED is UNKNOWN/retained, never an automatic takeover. Process-local phase prevents recursive mutex ownership becoming double admission. Mutex possession grants no operation, CA or credit authority.

The successor reuses its existing bounded stream log as the durable first claim. For a FUTURE approved positive command ONLY, PowerShell creates papacc-psr-75330d11cc7e4123ae62eadc9a59c2f5.launch.log with CREATE_NEW/no overwrite in the approved protected LAB parent, checks path components for reparse, writes and flushes exact attempt/owner PID/creation header before invoking native qualifier. Native checks the held parent/config identities/SDs, binds an ORIGINAL process handle and creation time, opens the exact log with no reparse/multilink, checks header and native log SD using the existing scm_descriptor validator, and retains its original file handle. Text/PID alone does not establish custody/authority. Operator/image/boot/service/approval/config/dependency checks are independent. Failure denies before image/diagnostic/rebind/Start; log remains a non-replayable claim, not a success receipt.

Ordinary admission checks both durable claim and intent before AND after acquiring the shared primitive. Only the exact LAB holder with the original bound launcher/file may proceed through its own marker. A second launcher cannot CREATE_NEW the same log; a different process cannot reuse its predecessor's PID/creation binding. This covers UNKNOWN before intent creation: disappearance of the mutex/process cannot erase the first log. It does not infer cleanup from disappearance.

After exact confirmation/preflight the same owner consumes the authorization once with the existing intent concept, now placed in the protected parent as papacc-psr-75330d11cc7e4123ae62eadc9a59c2f5.intent, CREATE_NEW/flush/no overwrite. This replaces the local native-intent producer; it is not a second journal. Its SD is assigned only at new-object creation (no existing ACL setter). Failure of creation/write/flush/descriptor release retains the owner; there is no retry, deletion or rollback. Only a consumed exact-LAB lease may enter effect state. An ordinary root lease cannot consume or grant LAB authority.

Stop prevents subsequent consume/effect. UNKNOWN is irreversible in the live owner and keeps all references. Release requires caller's factual quiescence; the real qualifier derives it from original-process termination and existing guarded cleanup, not timeout/exit-code alone. It closes launch/process/intent refs and releases/closes the mutex with checked results. A clean release never deletes/rearms the persistent one-shot markers or refunds credits; same attempt remains consumed. No automatic post-crash/reboot recovery. One-shot opt-in profile remains closed after consumption pending a separately governed disposition; default product and independent historical resources are not retired or frozen by this mechanism.

[CreateMutexExW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexexw), [mutex lifetime/abandonment](https://learn.microsoft.com/en-us/windows/win32/sync/mutex-objects), [CREATE_NEW semantics](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew). Native object-name protection is a synchronization condition; the accepted policy, original identities, immutable pins, one-shot records and explicit future approval remain separate conditions.
