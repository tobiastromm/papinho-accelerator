## Format choice

Recommend B: `.papacc` authenticated encrypted envelope containing a deliberately restricted ZIP (STORE only). Ordinary ZIP tools will not open the outer file: UI must say “pacote Papinho protegido”, not promise general password-ZIP interoperability. Inner archive is standard ZIP32 but its restricted profile is parsed only after authentication. This keeps owner’s one-file ZIP-content preference while explicitly disclosing the outer-format difference.

| Alternative | Assessment |

| A ZIP strong encrypted profile | ZipCrypto forbidden; generic “AES ZIP” is not an exact interoperable contract. No qualified encrypted ZIP reader/writer/profile found in the existing credential importer/BearSSL APIs examined. This is offline interchange, not PACC wire or a new network listener. No PCP1 auto-detection, migration or downgrade. Unknown version/suite rejects explicitly; never try ZipCrypto/plain ZIP/advanced import as automatic fallback.

## Cryptographic profile — proposed exact suite 1

AEAD: ChaCha20-Poly1305 RFC7539/8439 semantics, key32bytes, nonce12bytes, tag16bytes, header+signer SPKI as associated data. Fixed full16byte tag comparison through reviewed constant-time utility. Existing `br_poly1305_ctmul32_run` with `br_chacha20_ct_run` is a portable implementation candidate; the header explicitly requires the caller to check the computed tag. Decryption can produce unauthenticated plaintext internally: quarantine it, never ZIP-parse/use it before tag verification, and wipe on failure. No new construction or partial-tag acceptance.

KDF: PBKDF2-HMAC-SHA256, dkLen32, random16byte salt, fixed600000 iterations in suite1. This numeric work factor is a PROPOSED engineering selection, not an accepted security standard claim or measured NT4 latency. Exact field equality before work prevents attacker-selected unbounded iteration count; no automatic downward tuning. If real NT4 usability/Stop latency or ED11 fails, revise proposal before acceptance, never silently weaken suite. Local BearSSL KDF header documents HKDF, not a verified PBKDF2 API; use a selected, licensed, vetted standard PBKDF2 implementation/adapter with HMAC primitives, known-answer/differential tests and optimized VC6 review before shipping. Do not invent `br_pbkdf2`, handwritten new KDF or assume PBKDF2 exists in PST.

Unlock baseline: server CSPRNG generates20random bytes encoded as exactly32 uppercase RFC4648 Base32 characters A–Z2–7, no padding;160bits of random secret. No user-chosen weak password in suite1. UI may visually group it, but input strips only ASCII spaces/hyphens and folds ASCII lowercase; resulting exact32 characters required, no locale/Unicode normalization. KDF takes those32ASCII bytes. Secret shown/delivered only via approved protected channel distinct from package; never CLI argument, ENV, manifest, pipe transcript or audit. Package+password compromise reveals client key. Password does NOT authenticate issuer. This baseline avoids relying on memorable-password strength while KDF performance remains a mandatory gate.

Fresh random salt and nonce per newly protected package, from approved CSPRNG with fail-closed status; never derive from PID/time/epoch/serial. Unique password per new package; repeat export copies exact protected bytes without re-encryption/nonce reuse computation. Reprotection/renewal requires fresh password/salt/nonce and explicit administrative transaction.

Issuer authenticity: RSA2048/e65537 RSASSA-PKCS1-v1_5 SHA256 signature by an explicitly approved administrative package signer, not automatically the channel key/CA. Existing RSA verify primitives are candidates, not permission to reuse a key for another purpose. Full signer SPKI SHA256 must be independently verified through an authenticated admin channel or already approved local trust before accepting file-supplied key. Embedded SPKI and a matching self-reported hash do not authenticate anything. On first Browser, single import dialog includes independent full fingerprint/server confirmation; a second key file or prepared Browser is not required. Without independent reference/confirmation import stops. No silent TOFU or trust from password/contained CA. Public package signing occurs after encryption; verify signature before KDF to reject unsigned substitution/parameter DoS, then verify AEAD before ZIP parsing.

Local attempt limit: three password failures per import-dialog session, then require explicit close/reopen; no auto retry, no weakening. This is UX/online work control only, NOT prevention of offline brute force or a global single-use proof. Do not persist passwords. Each KDF step must permit bounded cancellation using the existing UI work/lifetime mechanism; exact cancellation-latency qualification is pending. No synchronous unbounded owner Stop delay or new operational supervisor.

## Envelope layout

All outer integers unsigned big endian. Fixed92byte header:
magic8 ASCII `PACCMP02`; u16 version2; u16 suite1; u32 flags0; u32 total_length; u32 ciphertext_length; u32 iterations600000; salt16; nonce12; signer_SPki_sha25632; u32 signer_SPki_length.
Then signer SPKI DER1..1024bytes (RSA2048/e65537 only), ciphertext1..65536bytes, AEADtag16, signature256. Exact total =92+SPKI_length+ciphertext_length+16+256, no trailing bytes; reject total>131072, arithmetic overflow, unknown flags/suite/version or unsupported key before expensive work. Extension is not format detection. Header spellings are field descriptions, not native C structs.

AAD is exact header+SPKI bytes. Signature covers ASCII `PAPACC-COMPLETE-MANUAL-V2`, zero byte, exact header+SPKI+ciphertext+tag. Signature does not include itself. File hash is only transfer/audit integrity, never authenticity. Hold immutable input bytes/identity across verification/use; no path reread swap. All unauthenticated fields have bounds before allocation; unsigned or untrusted signer is denied before decryption.

## Restricted ZIP and logical content

Exactly five entries in fixed order, byte-exact case-sensitive ASCII names: `ca.der`, `cliente.der`, `cliente.pk8`, `config.bin`, `issuance.bin`. No paths, directory entries, alternate streams, NULs, links, extra members, duplicate names or case folding. ZIP32 local headers and central directory must agree exactly on names, CRC32, sizes, offsets and order; method0 STORE, flags0, version-needed20, fixed DOS timestamp date0x0021/time0; no ZIP encryption/data descriptors/ZIP64/extra fields/comments/multidisk/self-extracting prefix/trailer. Exactly one EOCD with disk0 and entries5. Reject overlaps, holes/hidden data and inconsistent lengths. CRC checks are corruption checks only; outer signature/AEAD provide security. Little-endian ZIP fields follow ZIP convention, distinct from big-endian envelope/config integers. Zero decompression, no disk extraction.

Caps PROPOSED: ca.der16384, cliente.der16384, cliente.pk8 8192, config.bin4096, issuance.bin4096bytes, all nonempty; total ZIP plaintext<=65536. This restricts supported chain sizes rather than increasing existing CS_LIMIT1MiB/material. ca.der single approved channel CA DER; cliente.der single leaf DER, directly verifiable under the selected supported issuer chain profile. Unsupported intermediate-chain deployments deny, never strip needed certificates. cliente.pk8 unencrypted PKCS8 PrivateKeyInfo v0 only INSIDE encrypted ZIP; external file never contains that plaintext. No CA private key, token, operational grant, password or Session material. Plaintext ZIP is never written to distributed file or ordinary temp storage.

config.bin: magic8 `PACCFG02`, u16 version2, u16 count16, then ascending unique TLVs u16tag/u32length/value, no padding/trailer/optional fields. Tags: 1 ExpectedServerName DNS ASCII1..253; 2 port u16 nonzero; 3 server leaf DER SHA25632; 4 channel CA DER SHA25632; 5 config domain32; 6 config revision u64nonzero; 7 policy identity32; 8 policy revision u64nonzero; 9 ALPN eight bytes `papacc/1`; 10 SecurePrincipal profile u16=1; 11 package identity32 CSPRNG bytes; 12 client leaf SHA25632; 13 recipient label UTF8 1..128/no controls; 14 issued_at UTCseconds u64; 15 import_not_before UTCseconds u64; 16 import_expires UTCseconds u64. DNS labels LDH1..63, no leading/trailing hyphen, wildcard, empty label, IP literal, NUL or trailing dot. Values refer to actual approved committed configuration; revisions are provenance, not Browser assertion of remote CURRENT. Label is intended recipient metadata, not device authentication. Package signer identity is outer header. No Browser prerequisite/CSR field.

issuance.bin: magic8 `PACISS02`, u16version2, u16count5; same TLV rules. Tags1 approved issuer binding SHA25632; 2 issuer CA DER SHA25632; 3 client certificate serial unsigned canonical big-endian1..20bytes/no redundant leading zero; 4 immutable issuance correlation UTF8 1..128/no controls; 5 renewed predecessor client-leaf SHA256, length0 for first issue or32 for renewal (explicit absence). Returned certificate and administrative record must agree. No hidden credential/Principal fallback in empty fields.

Certificate/key correspondence, clientAuth/EKU/KeyUsage, CA trust/purpose, validity, issuer binding, expected server name and authenticated contents all require validation. Existing R1 material validator proves framing/CA/key match, not complete package authenticity or chain/time/revocation. Certificate/server rotation requires explicit reviewed replacement; initial included server fingerprint is confirmation evidence, not an implicit permanent leaf pin bypassing normal validation. Site HTTPS trust remains SYSTEM under its distinct profile; included channel CA never approves Site TLS.

## Custody and lifecycle contract

GENERATE -> ISSUE -> PROTECT -> PACKAGE -> EXPORT -> IMPORT -> VALIDATE -> COMMIT are separate factual states. Key generation/issuance are not authorized by this task. Protected work belongs to durable admin request owner under same root with bounded credits. Generate individual RSA2048/e65537 client key through approved crypto provider; CA key never involved in client-key generation. Send only public CSR/key to approved issuer. Full private material exists transiently in necessary provider/memory buffers; core uses handles/references where possible. Every copy/scratch must have owner, size, wipe and retained-failure disposition.

PROTECT/PACKAGE requires plaintext archive only in reserved private memory, output encryption directly to protected staging. No plaintext temp file, command arguments, logs, crash dump claims or ordinary export. Wipe password/KDF key/client-key/intermediate/archive buffers through reviewed non-elidable erasure at quiescence, including failure/cancel; do not claim absolute physical erasure, locked-memory guarantee, swap/dump exclusion or historical backend encryption at rest. If implementation cannot keep required transient copies inside reserved custody, STOP.

Server retains only encrypted protected package (when configured for later export), public certificate/issuer/journal/provenance and client mapping; no persistent plaintext client private key or password recovery record. Protected retention duration/capacity require approved admin policy before creation; no default infinite retention. A protected staging path must be selected with ownership/ACL/reparse-safe checked create/write/flush/close/atomic publication, not arbitrary caller file overwrite. These mechanisms are not claimed implemented.

Issue uncertain => RECONCILIATION_REQUIRED/query existing issuer correlation, no blind duplicate certificate. Issued but root publication failed => issued-unpublished/deny, reconcile or revoke; deleting key/export does not undo issuer fact. Protected export CREATE_NEW/full-write/flush/close checked; partial or uncertain export not SUCCESS, retain owned resources as necessary. Retry exports exact protected bytes, not a second identity. Missing password/package => no plaintext server recovery; new approved renew/revoke/reprotect workflow. A copied package plus password can clone the same credential: offline package cannot enforce one physical computer. Administrative recipient and individual-device intent must be explained, not falsely attested by hostname/PID/label.

Compromise/lost uncontrolled copy requires persistent server revoke and new key/certificate under explicit renewal; local removal != remote revoke. Renewal preserves stable Principal only via approved server mapping, never fingerprint identity. Proposed active revocation: deny new authentication/admission at committed revision; invalidate affected pending issuance/exports; notify existing owner paths to revalidate/Stop affected Sessions/ops, preserve first cause and truthful non-clean/retained outcomes, ED08 and Model E; no forced free/DESTROYED, no destructive retry. Exact checkpoints/propagation-bound implementation needs separate accepted contract and qualification; no claim of instantaneous/global revocation or successful revoke while acknowledgement uncertain. Unaffected Sessions coexist, snapshot capabilities never broaden. This active-policy proposal does not modify existing runtime guards.

## Import, rollback and duplicate rules

Single UI operation: select file -> bounded envelope/signature/trusted-signer checks -> masked unlock -> AEAD -> in-memory ZIP parse -> confirm server/recipient/trust independently -> validate actual materials -> prepare existing store/draft -> explicit confirmation -> existing gate+ActiveConfiguration flip -> candidate_committed. Retain “Configurar segurança — importação local” and advanced separate CA/cert/key selection. No second store, commit or runtime routing branch.

Exact duplicate committed package hash/identity/server is ALREADY_IMPORTED/no new generation. Same identity different signed bytes is INVALID; old-revision replay never replaces current state automatically. Replacements/renewals need explicit reviewed transition. Record replay/import provenance in same generation metadata and bounded retained journal; no separate authority/database. Across offline machines, global single-use cannot be proven; live authorization/revocation remains server responsibility. Expired/unverifiable wall clock/package notBefore/notAfter denies. issued_at<=not_before<expires inside relevant certificate validity; deployment expiry ceilings and retention limits must be approved, no invented universal TTL.

Cancel/failure before flip leaves previous committed config intact, cleans only owned unconsumed staging and wipes secret copies when safe. Failure after flip reads back durable generation; never pretend rollback or issue a second credential. Removal/retirement waits for committed noncurrent state and zero leases; failure/UNKNOWN retains dependencies and original credit. Process exit, timeout, package import success or remote FINAL is not factual teardown. No Model E weakening, alternate cleanup or owner-thread blocked by KDF/archive work.
