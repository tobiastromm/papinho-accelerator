# Identity, trust and possession — factual review

The existing owner receipt supplies an EK fingerprint and one certificate DER fingerprint, not DER, RSA/ECC parameters, canonical SPKI, issuer, signature or an authenticated chain. Neither fingerprint can be inverted to perform the absent checks. The old query is not repeated by Codex. Intel/firmware metadata is not a unique authenticated device identity. A current machine name and boot event computer field are different metadata sources, not a device-generation oracle.

Microsoft documents that Get-TpmEndorsementKeyInfo.PublicKey is AsnEncodedData; AdditionalCertificates can include enterprise-registered certificates, whereas ManufacturerCertificates can include manufacturer/platform certificates. Therefore the sole AdditionalCertificates entry cannot simply be treated as an Intel endorsement certificate or a trusted anchor. Manufacturer name alone is insufficient to select an Intel root/issuer. No trust anchor was downloaded, installed or designated and no live revocation/network query ran.

Prepared a discriminating public-byte collector, NOT EXECUTED. Unlike the previous metadata query it obtains raw ASN.1 public key bytes and only the exact already-observed certificate DER, then compares both original fingerprints. Type/size, script/helper pins, already-elevated x64 PowerShell5.1, no impersonation and source-module guards remain. New or multiple certificate/encoding/key mismatch => DENY. It requests no private key or ownerAuth. The public material must stay local; the owner should not paste the base64 certificate/key into public reports. It grants no trust, freshness, hardware generation, custody or Q4 authority. Internal cmdlet context closure remains unobserved.

OfflinePublicEvidence is an analysis helper, not a product backend or admission mechanism. It checks bounded byte inputs, separate typed fingerprints, canonical SPKI equality, EK-purpose/CA constraints and an explicitly supplied root bundle with OpenSSL default trust stores disabled and an explicit time. No AIA/revocation fetch or trust-store installation is performed. Purpose 'any' prevents accidental TLS-purpose substitution; EK-specific checks are separate. Offline revocation is UNKNOWN. Its path-based input and tool hashes are DATA checks, not original-handle protection; it cannot satisfy RAW1/device authenticity and always reports authority DENY. Positive/negative contract tests use mock parser outputs, plus a real OpenSSL rejection of malformed DER. No valid actual EK certificate/chain has been evaluated. Extra chain intermediates and exact manufacturer profile still require byte-level review once public material exists; textual EK-extension parsing is fail-closed preparation, not a qualified universal X.509 validator.

## Credential activation experiment

Implemented RSA2048/SHA256 software fixture: OAEP label IDENTITY plus terminator, KDFa STORAGE/INTEGRITY, Windows CNG AES128-CFB128 of a TPM2B30-byte synthetic challenge, HMAC over encrypted identity and AK Name. RSA keys are CNG ephemeral software keys; public-only key is used to make the credential, private software counterpart to open it. No persisted key, CA, certificate issuance, TPM TBS call, AK or EK hardware object is created. Synthetic seed/challenge are public fixture vectors, never operational credentials. KDF outputs independently cross-checked with Python hashlib/HMAC. Checked BCrypt close is inherited from prior fixture; managed RSA/handle Dispose returning is reported as such, not a TPM internal-context close proof.

Debug and Release each pass364 assertions: clean round trip, private-key mismatch, wrong OAEP label, every byte of encrypted seed/ciphertext/MAC mutated, AK Name mutation, malformed inputs, ephemeral-key checks and KDF vectors. This is offline software interoperability within the fixture; no TPM simulator/reference implementation/native interoperability or hardware possession claim. Only RSA/SHA256/AES128 fixture profile is covered, not unknown actual EK algorithm or ECC. Real salted TPM authorization/session/ActivateCredential response authentication is NOT implemented or enabled by this fixture.

An actual possession observation needs a fresh unpredictable challenge bound to the approved EK and qualified AK Name/context, a valid authenticated response, and original live TPM/session/process continuity. ActivateCredential success proves the specified relationship under the approved trust/threat model, not physical locality against a malicious proxy or NV generation continuity. A chain check alone also does not prove private-key possession. Device origin, live possession and non-restored NV generation are three separate obligations.

Existing-object read-only inventory may identify a reusable qualified EK/AK, but must not adopt an unknown handle/Name as owned. If no qualified AK exists, CreatePrimary/Create/Load and policy/authorization sessions introduce transient TPM state; these real commands are outside this task's execution and require their own exact bounded approval. Persisting a key, EvictControl, NV mutation, hierarchy changes, certificate enrollment, signing/quote and network attestation are not silently included. A complete native request cannot invent AK/EK algorithm/template/Name or endorsement authorization that has not been observed/qualified.
