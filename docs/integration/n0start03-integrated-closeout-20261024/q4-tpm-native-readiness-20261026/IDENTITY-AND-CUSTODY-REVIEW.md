# Device identity and authorization custody

Manufacturer INTC/firmware500.14.0.0/interface3 and counter-capability fields identify a product family/available interface, not a unique authenticated device. Original generation continuity, exclusion of a co-restored vTPM and resistance to Clear/deletion/redefinition remain unproved. TPM NV Name binds public area, not original provisioning lifetime. A WRITTEN transition changes the expected public metadata; use exact pre/post area and root-approved history, never blind same-Name adoption.

The official EK public-information cmdlet was investigated via metadata-only queries. In this token it returns an administrator-required STRING; initial null-property/count projection was invalid and was corrected. No EK fingerprint, manufacturer certificate presence, chain or proof of possession is established. A pinned manual public collector for an already elevated PowerShell5.1x64 is prepared; it does not query ownerAuth, export private key, build network chains or issue NV commands. Public EK hash/cert metadata would still require approved trust validation and a qualified live possession/continuity binding; copied public certificates alone cannot authenticate the current TPM endpoint. No TPM attestation/signature operation was attempted.

Project source inventory found the existing CA key owner uses Software KSP for a distinct signing purpose; it is not a generic vault for TPM hierarchy/index passwords. No existing DPAPI/CredWrite/TBS ownerAuth custody implementation was found in reviewed source. Do not reuse CA keys, copy KSP files, store plaintext secret in root/manifests, invent a second secret registry, infer owner password from admin status or use empty-password fallback. Windows may not retain full hierarchy auth; availability must be factually established by authorized custodian without exposing values in this report. No ownerAuth read attempted.

The proposed index secret is32randombytes, generated only in an approved future provisioning ceremony. Custody must bind device/index/root/approval, survive intended reboot through an approved encrypted custody mechanism or operator-controlled existing secure custody, support in-memory HMAC use and prevent logs/argv/ENV/plaintext persistence. Neither mechanism has been designated/proved here. A future request must name the actual custodian/mechanism and live binding; an arbitrary file path or SecureString label is not a custody proof. Avoid duplicate transient secrets, preserve borrowers until close and never claim guaranteed wiping from managed GC. A disappearing secret strands the index and denies use; it does not authorize deletion, reset, credential recreation or refund.

NO_DA is clear in the candidate, so wrong auth could affect dictionary-attack protection; real wrong-password testing is excluded. One failed authorization is STOP, not a search loop. No command blocking policy change. Reinstallation/replacement/clearing does not make previous root/history virgin; no automatic recovery/re-provisioning. Offline operation is possible only once policy, original identity and credentials are available locally under the approved model; offline inability to establish trust or authority remains DENY.
