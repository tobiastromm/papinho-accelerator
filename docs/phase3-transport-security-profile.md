# Phase 3 Initial Transport Security and Credential Profile

Status: authoritative Phase 3.A2A mechanism and credential design freeze. This
profile refines the [Phase 3 Security Architecture and Threat Model](phase3-security-architecture.md).
It selects an interoperable security profile, not a TLS library or backend, and
adds no implementation or PACC wire bytes.

Normative terms apply to the future protected production implementation.

## Selected profile

| Property | Initial profile |
|---|---|
| Transport Security protocol | Standard TLS |
| Minimum/only version | TLS 1.3 only |
| Server authentication | TLS 1.3 external PSK proof using the provisioned client/server credential relationship |
| Client authentication | TLS 1.3 external PSK proof, with one credential per authorized client |
| Credential granularity | Independently provisioned per-client credential; global shared PSK forbidden |
| Forward secrecy | Required through `psk_dhe_ke` |
| PSK-only exchange | `psk_ke` forbidden |
| 0-RTT | Disabled; no PACC message may be early data |
| Resumption | Disabled/deferred; full authentication on every connection |
| Cleartext/TLS fallback | Forbidden when security is required; no TLS 1.2 fallback |
| DATA principal binding | Same authenticated principal as CONTROL required |
| Ticket-alone authorization | Forbidden |
| Credential identifier secrecy | Not promised; identifier is opaque and non-personal |
| Credential identifier | Exactly 16 opaque bytes in the initial credential model |
| Secret entropy | Exactly 32 CSPRNG-generated bytes (256 bits), unique per credential |
| Cipher suites | `TLS_CHACHA20_POLY1305_SHA256` required; `TLS_AES_128_GCM_SHA256` allowed |
| Key exchange group | Modern ECDHE required; exact required group frozen by 3.A2B after X25519/P-256 feasibility |
| ALPN | Required, exact opaque value `papacc/1` |
| SNI | Not required in the initial direct-listener profile |

TLS, PACC framing, Control protocol and software versions are separate version
domains. Successful negotiation in one does not substitute for validation of
another.

TLS 1.0 and 1.1 are forbidden, and failure of TLS 1.3 must not trigger TLS 1.2
or cleartext. Any future second secure profile requires an explicit design and
administrative policy; it cannot be discovered through fallback. Production
fails closed if the required backend, profile or credentials are unavailable.

The profile follows the standard TLS 1.3 distinction between `psk_dhe_ke` and
PSK-only `psk_ke`, and the external-PSK guidance to combine PSKs with ephemeral
key exchange. See [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) and
[RFC 9257](https://www.rfc-editor.org/rfc/rfc9257.html). PapinhoAccelerator does
not design encryption, MAC, key exchange, binders or a replacement handshake.

## Authentication-model comparison

| Criterion | A: TLS 1.3 mTLS | B: server TLS + application client auth | C: TLS 1.3 per-client external PSK |
|---|---|---|---|
| Standardness | Standard TLS | TLS plus a new Papinho auth protocol | Standard TLS |
| Server/client authentication | Mutual certificates | Server in TLS; client in application | Mutual proof of provisioned PSK |
| Forward secrecy | Available with ephemeral exchange | Available for TLS; app auth must be reviewed | Required with `psk_dhe_ke` |
| Compromise scope | Client private key can be isolated from server | Depends on credential design | One client's symmetric PSK affects that relationship only |
| Provisioning/rotation/revocation | Mature PKI possibilities, more machinery | New credential and wire machinery | Explicit bounded per-client records |
| Multiple clients / DATA binding | Strong certificate identity | Requires app principal design | Direct stable credential-to-principal mapping |
| NT4/VC6 impact | Certificate parser, chain validation and APIs/code | TLS plus additional auth code | Portable TLS external-PSK support; no certificate parser |
| Wall clock / PKI | Validity periods and chain/trust provisioning | Server certificate normally has these concerns | No certificate validity clock or PKI |
| Code/memory/operations | Highest initial complexity | Two security layers and more messages | Smallest initial operational model |
| Future management | Strong enterprise fit | Custom management burden | Straightforward headless/GUI credential records |

Model C is selected for the first secure baseline. It mutually authenticates
inside a reviewed protocol, supports a stable per-client principal on every
CONTROL/DATA connection, avoids a custom application authentication exchange,
and avoids certificate parsing, chain validation and trusted certificate time
on NT4. A client can bundle portable TLS rather than rely on the legacy OS.

Model A remains a credible future enterprise profile: public-key client
credentials reduce symmetric-secret exposure at the server and fit larger PKI
deployments. Certificates do not require public Internet PKI—a private CA or
pinning is possible—but still require chain/trust provisioning, parsing and
normally certificate-validity wall clock. It is not the initial profile.

Model B is rejected for the initial baseline because it adds Papinho message
IDs, replay/timing/error-disclosure surface and duplicate credential-proof code
without benefit when TLS external PSK already performs mutual authentication.
No `AUTH_REQUEST`, login, password or custom challenge is introduced.

External PSK has explicit costs: the symmetric secret exists on both endpoints;
the server stores every client's secret; provisioning must already be secure;
rotation and revocation are explicit operations; correct TLS 1.3 external-PSK
support is mandatory; and the PSK identity is ClientHello metadata and may be
observable. Compromise of client A's PSK can impersonate client A to the server
and potentially the server to client A. It does not reveal independent client
B credentials. Server credential-store compromise exposes stored client PSKs,
even though endpoint/root compromise is outside the network threat model.

## Cipher, group and extension policy

Forward secrecy is mandatory for CONTROL and DATA. Clients offer only
`psk_dhe_ke`; servers reject `psk_ke`. The initial profile disables TLS early
data because of replay, authorization and ticket ambiguity, and disables
resumption until principal binding, revocation, lifetime and replay behavior
receive a separate freeze. Thus every CONTROL and DATA connection performs a
full TLS 1.3 external-PSK authentication.

`TLS_CHACHA20_POLY1305_SHA256` is required for Papinho endpoints because it is
a standard TLS 1.3 AEAD suitable for portable software on CPUs without AES
acceleration. `TLS_AES_128_GCM_SHA256` is allowed to support efficient modern
server/client implementations, but is not required for Papinho interoperability.
No obsolete cipher suite is allowed. 3.A2B must validate implementation size
and performance rather than weakening this policy.

`psk_dhe_ke` requires an approved modern ECDHE group. X25519 is the preferred
candidate and P-256 the compatibility candidate. 3.A2A deliberately does not
make one mandatory before the legacy/backend spike measures availability,
correctness, code size, stack and CPU cost. 3.A2B must freeze at least one
mandatory interoperable group; it may not fall back to `psk_ke`.

ALPN is required to bind TLS connections explicitly to the PapinhoAccelerator
application protocol and reduce cross-protocol confusion. The initial opaque
identifier is `papacc/1`; it identifies the protected application profile, not
the TLS, envelope, Control or software version. Unsupported/missing ALPN fails
the protected handshake. ALPN is the standard mechanism defined by
[RFC 7301](https://www.rfc-editor.org/rfc/rfc7301.html), not a custom TLS
extension. SNI is unnecessary for the initial direct Accelerator listener,
which has no virtual-hosting requirement.

## Credential and principal model

An initial client credential contains two distinct values:

```text
credential identifier: 16 opaque bytes
credential secret:      32 bytes of CSPRNG output
```

The identifier is bounded lookup metadata, not a username, email, hostname,
personal identifier, principal, runtime ID, Session ID, Channel ID or DATA
ticket. Its confidentiality is not promised. The secret is unique, high
entropy and never password-derived, runtime-ID-derived or generated by the
sequential Phase 2 ticket provider.

```text
opaque credential ID
    -> enabled credential record and secret lookup
    -> successful TLS 1.3 PSK-DHE proof
    -> stable internal authenticated principal
```

Unknown, disabled or revoked identifiers fail TLS establishment, close the
Connection before classification and create no Session. Network-visible errors
must not unnecessarily distinguish unknown ID, wrong secret or revocation.
Raw secret bytes never become an authorization identity or leave the security
backend. Authorization consumes the principal and policy references.

The same credential maps to the same stable principal across its CONTROL and
DATA connections. Multiple credentials may map to one principal to support
rotation without changing authorization identity:

```text
principal
    +-- current credential
    +-- next credential during a bounded rotation window
```

The store must be bounded and must allow an administrator to disable/revoke
one credential independently. Arbitrary unknown identities never create
principals.

### Credential lifecycle

| Stage | Owner | Secret | Public metadata | Provisioning | Revocation | Rotation |
|---|---|---|---|---|---|---|
| Generation | Trusted administrative tooling (future) | 32 CSPRNG bytes | 16-byte opaque ID, profile | Offline credential bundle | Not yet active | New credential generated |
| Server import | Separate server credential store | Client PSK | ID, enabled state, principal/policy references | Administrator import | Disable/remove record | Temporarily map old/new records to same principal |
| Client import | PapinhoBrowser credential storage | Matching PSK | ID and server trust/profile info | Administrator import over trusted offline path | Remove/disable locally after server revocation | Import replacement then retire old credential |
| Runtime | TLS backend only for explicit lifetime | Secret-derived TLS state | Principal reference, TLS/profile state | Store lookup, never CLI secret | New handshakes fail when revoked | Existing-connection policy decided later |
| Retirement | Store owners | Removed/cleared as practicable | Audit metadata may remain without secret | Administrative action | Definitive disable | End rotation window and retire old record |

Initial provisioning is explicit and offline: trusted tooling will generate a
bundle, the administrator imports the server record, and imports the matching
client credential into PapinhoBrowser. Bundle format and NT4 storage are not
defined here. Interactive pairing is deferred because it would require another
authenticated bootstrap protocol.

`Credential Source != Credential Store/Model != Authenticated Principal`.
`PAPACC_SERVER_CONFIG` must not contain raw PSK/private-key bytes; a future
configuration may reference a separately owned store. Normal production CLI
must not accept `--psk <secret>` or `--password <secret>`; it may eventually
refer to a store or bundle import operation. Client storage must keep ID,
secret and expected server/profile information outside ordinary source and,
where practical, ordinary plaintext configuration.

Secret-bearing buffers require explicit lifetime and cleanup. Concrete
zeroization guarantees wait for backend/API evaluation, including what VC6 and
MSVC can reliably provide.

## Connection, Session and authorization flows

Every TCP connection establishes TLS independently before PACC classification.
Clear `PACC`, `CONTROL_OPEN` or `DATA_ATTACH` bytes sent to a required-secure
listener fail TLS and never reach `PAPACC_CONNECTION_CLASSIFIER`.

```text
TCP accept
    -> TLS 1.3 external-PSK + ECDHE handshake
    -> authenticated principal and selected profile
    -> decrypted PACC Framing
    -> CONTROL_OPEN creates internal ESTABLISHING Session
    -> CONTROL principal association + Session authorization
    -> CONTROL_ACCEPT
    -> Session ACTIVE and usable
```

`CONTROL_ACCEPT` remains the peer-visible indication that all required
transport authentication and CONTROL authorization gates passed. Its existing
four-byte payload need not change: TLS authentication happens below PACC and
the current Phase 2 exchange already uses it as successful structural
establishment. The strengthened production preconditions do not renumber or
alter `0x0001`--`0x0006`. The client must not use a Session before receiving
`CONTROL_ACCEPT`.

TLS authentication is not authorization. Server policy separately decides
Session access, DATA attachment, resource limits, future capabilities and
network egress. Authentication never grants all Phase 4 capabilities or
`NETWORK_EGRESS_ACCELERATOR`.

```text
DATA TCP accept
    -> TLS 1.3 external-PSK + ECDHE handshake
    -> authenticated DATA principal
    -> decrypted PACC Framing
    -> DATA_ATTACH structural ticket
    -> resolve target Session without consuming ticket
    -> DATA principal == CONTROL Session principal
    -> DATA authorization
    -> atomic conditional ticket consume
    -> DATA bind
    -> DATA_ACCEPT
```

Required attach condition:

```text
authenticated DATA principal == authenticated CONTROL Session principal
AND valid structural ticket
AND DATA attachment authorization
AND existing Session ACTIVE / CONTROL BOUND invariants
```

Ticket knowledge alone is never authority. Principal compatibility is checked
before one-time consumption so a wrong principal cannot burn a legitimate
client's observed/guessed ticket. The current Phase 2
`association_manager_consume(ticket)` consumes immediately; 3.D must design a
failure-atomic `resolve/inspect` plus conditional consume, or an equivalent
`consume_if_authorized`, without exposing Session identity on wire.

A separate Connection Security Context maps runtime Connection ID to state,
selected TLS profile and principal. Successful CONTROL association copies a
principal reference into a separate Session Security Context. Neither raw
secrets nor TLS backend handles enter `PAPACC_CONNECTION` or `PAPACC_SESSION`.

## Close, failure and scheduling

The future backend must distinguish clean TLS `close_notify`, fatal
integrity/security failure, and raw transport EOF without a clean secure close.
Unexpected truncation must not be reported as legitimate EOF where TLS requires
the distinction.

| Failure | Scope |
|---|---|
| Unknown/wrong/disabled/revoked PSK or malformed TLS | Close candidate before classifier; no Session |
| CONTROL TLS failure before/after Session creation | Close CONTROL; existing lifecycle closes Session and all DATA |
| Candidate DATA TLS failure | Close candidate DATA; preserve Session/CONTROL/other DATA |
| Established DATA integrity failure | Close that DATA Channel; preserve Session/CONTROL/other DATA |
| DATA principal mismatch | Close candidate without consuming ticket; preserve Session/CONTROL |

Security handshake work participates in fixed Connection/security-slot
capacity, `FD_SETSIZE`, single-`select()` round-robin scheduling, bounded work
and bounded allocation. It has an independent PAL-monotonic deadline selected
in 3.E, not an implicit reuse of the current 15-second classifier deadline.

Production security is required. A future insecure test/developer mode is not
part of the production profile and, if ever added, must be explicit, opt-in,
prominently labeled, non-default and incapable of receiving fallback traffic.
The preferred topology is one protocol endpoint whose configured security
policy decides acceptance, not permanent parallel secure/insecure products;
no port is added here.

## Metadata and logging

TLS does not hide peer IP addresses, ports, connection timing, traffic volume
or necessarily the opaque external-PSK identity. No PSK identity may contain
personal or sensitive meaning.

No log level may emit PSK secrets, bundles, binders/proofs, traffic secrets or
session keys. Opaque credential IDs are not logged by default; a later explicit
redacted diagnostic design may reconsider their operational value.
`--log-level off` remains housekeeping, not permission for unsafe logs.

## Backend-independent 3.A2B compatibility spike

This profile is intended to interoperate across different compliant server and
client backends. It does not select OpenSSL, mbedTLS, wolfSSL, BearSSL, Schannel
or any other library. Existing use of a library elsewhere would not prove
suitability, and Win32 does not imply Schannel.

3.A2B must compile/probe candidate backends against:

- Accelerator MSVC build and PapinhoBrowser NT4/VC6/C89 constraints;
- license and intended-distribution compatibility;
- TLS 1.3-only external PSK and correct per-client identity lookup;
- exclusive `psk_dhe_ke`, with no `psk_ke`;
- required ChaCha20-Poly1305 suite and allowed AES-128-GCM suite;
- X25519 and P-256 support, selecting at least one mandatory group;
- ALPN `papacc/1`, disabled 0-RTT and disabled resumption;
- nonblocking incremental handshake/read/write and custom transport/socket
  integration compatible with the current scheduler;
- clean close, truncation and fatal-error signaling;
- CSPRNG integration and secret lifetime/cleanup capabilities;
- handshake CPU cost, memory footprint, code size, stack use, dependency
  footprint and build complexity on legacy targets.

No dependency may be added before its license is recorded and found compatible.
3.A2B may report the profile infeasible only with concrete evidence; it must not
silently weaken TLS version, forward secrecy or algorithm policy to reuse an
available backend.
